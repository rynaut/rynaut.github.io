What fits on a 6 GB laptop GPU

Five models, three context lengths (4,096, 32,768 and 131,072 tokens) and two KV-cache types, run on one RTX 3050 6GB Laptop GPU. Each of the 30 cells is fits, spills or OOM. Every cell is a single run.

Single run. One run per cell, not an average and not a benchmark. Speeds vary with what else the machine is doing: the control below repeated one cell five times and the first run was 2.6 to 3.7 times slower than the other four, cause not identified. Read the status columns, treat the speeds as indicative.

The 30 cells (table)

Fits: the run exited 0 and the llama.cpp log's device buffers (model + KV cache + compute) add up to at most the 6,143 MiB the card reports. Spills: the run exited 0 but those buffers add up to more than 6,143 MiB, so part of the load lived outside dedicated GPU memory; the Windows "shared GPU memory" counter rose. OOM: the run failed with an out-of-memory message. Window = context length requested. KV = KV-cache element type. Speeds come from a fill run with a prompt of about 90% of the window (4,096 and 32,768 only; 131,072 cells are allocation only). Generation speed is from 8 generated tokens, so it is rough.

Median prompt speed fell from 1,170.66 to 127.99 tokens per second, a factor of 9.15. All ten runs exited 0 with no out-of-memory text (exit code and a log-text flag were recorded per run). What this does not show: the 32,768 window is also the one whose buffers (9,202.84 MiB) exceed the card, so window size and spill are not separated on this card. Say "a larger window, which spills", not "the spill alone costs 9x". The first 4,096 run (344.16) was the slow outlier, 2.6 to 3.7 times slower than runs 2 to 5; cause not identified. It stays in the median.

Worth a look, not explained

  • MiniCPM3-4B at 4,096 tokens: prompt speed 127.63 tokens/s with an f16 KV cache against 21.18 with q8_0 (repeats: 85.34 to 92.34 and 20.07 to 20.54). No CPU-fallback line in the logs; cause unknown.
  • MiniCPM3-4B's KV buffer in this build is 3,100 MiB at 4,096 tokens (f16), while the latent-cache formula for its multi-head-latent attention gives 139.5 MiB. I have not checked how this llama.cpp build stores that model's cache.

Reproduce a cell

:: 1. Download llama.cpp b12340 (Windows, CUDA 12.4) and the weights file from the table above.
:: 2. One cell: 32,768-token window, q8_0 KV cache, allocation only (prompt "Hello")
llama-completion.exe -m MODEL.gguf -c 32768 -ngl 99 -fa on -ctk q8_0 -ctv q8_0 -no-cnv --no-display-prompt --perf -n 8 -fit off -lv 4 -p "Hello"

:: 3. A fill run: the same flags with -f prompt.txt, where prompt.txt is this sentence
::    repeated until it is about 90% of the window in tokens (llama-tokenize.exe gives the count):
::    "The server allocates a key and value tensor for every layer and every token of every active sequence.
::     When requests arrive the scheduler reserves memory for the weights, the cache and the activations. "

:: 4. Read the result: -lv 4 prints "KV buffer size", "model buffer size" and "compute buffer size" lines; add them up
::    and compare with the card's total. For spills, watch the Windows counter while it runs:
typeperf "\GPU Adapter Memory(*)\Dedicated Usage" "\GPU Adapter Memory(*)\Shared Usage" -si 1
nvidia-smi --query-gpu=memory.used --format=csv,noheader,nounits

The measurement scripts that wrapped these commands (measure.py, matrix.py, control.py) are not yet published.
